Teaching your site to talk to AI

A hands-on look at the Web Model Context Protocol

The status quo

How agents browse the web today

The way a human with no other option would: by looking at the rendered page.

📸
Screenshots + vision

Slow, and only as good as the model's guess.

Brittle selectors

🕵️
Reverse-engineered DOM

Guessing what a button does from its label.

The problem

Why that breaks down

Slow

Every action needs a screenshot-and-guess round trip.

Fragile

A redesign silently breaks every automation built on it.

Ambiguous

No schema, no contract — just a best guess at intent.

No permission model

The page can't tell the agent what's safe to do on its own.

The idea

What if the page just told the agent
what it can do?

WebMCP: a browser API for pages to register callable, typed tools.

How it works

Three actors, one API

AI Agent
Decides what to do
Browser
Mediates via the WebMCP API
Web Page
Registers the tools it wants to expose
How it works

The page registers a tool

await document.modelContext.registerTool({
  name: "favorite_event",
  description: "Add an event to favorites",
  inputSchema: {
    type: "object",
    properties: { eventId: { type: "string" } }
  },
  execute: async ({ eventId }) => { ... }
});

The page decides what's callable — and exactly how it behaves.

Two ways to register

Declarative vs. imperative

<form toolname="search_events"
      tooldescription="Search events by keyword"
      toolautosubmit>
  <input name="query" />
  <button type="submit">Search</button>
</form>

The browser derives the tool from the form. Best for simple, form-shaped actions.

await document.modelContext.registerTool({
  name: "favorite_event",
  execute: async ({ eventId }) => { ... }
});

Full control over schema, execution and side effects. Best for actions that aren't a form submission.

Anatomy

Same shape, every tool

name + description tell the agent what it does. inputSchema tells it what to pass. annotations tell it what's safe.

How it works

The agent calls a tool

executeTool() runs your execute() callback and returns its result — the exact same path whether it's a real agent calling it, or you testing it by hand.

Security

Agents run inside your session

A tool's definition and its output both become part of what the agent reads and trusts.

🎭
Malicious manifests

A tool's name, description or parameters can hide instructions aimed at the agent, not the user.

☣️
Contaminated output

A tool from a trusted site can still return untrusted data — user comments, third-party content.

Both are indirect prompt injection: instructions smuggled in as data. Combine private data access, untrusted content and a way to talk back out, and you get the "lethal trifecta" — enough to exfiltrate a user's data.

Security

Defense in depth

Scope exposure with exposedTo so only origins you trust can see or call a tool at all.

Caveat: annotations are a hint, not a guarantee — an untrusted origin can lie about its own tool. Pair them with real controls: origin scoping, user confirmation, sandboxing.

Beyond the basics

What this unlocks

Context-aware

Tools can read the page's live state — no re-sending filters the UI already has.

Dynamic

Tools register and unregister at runtime with an AbortSignal.

Cancellable

A long-running call can be aborted mid-flight.

Not just data

A tool call can navigate the browser, not only read or write.

Try it yourself

Turning WebMCP on today

  1. Install Chrome Canary.
  2. Open chrome://flags/#web-machine-learning-model-context and set it to Enabled.
  3. Relaunch the browser.

  1. Install the WebMCP - Model Context Tool Inspector from the Chrome Web Store.
  2. Open any WebMCP-enabled page.
  3. Use its panel to inspect and call the page's tools.
